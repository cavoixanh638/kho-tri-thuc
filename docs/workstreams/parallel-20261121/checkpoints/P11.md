## Concrete findings and repro

1. **ORDER-01 (confirmed by source inspection and synthetic rendering contract; requires DOM test):** `LibraryViews` timeline collects rows into a `Map<day, Item[]>` grouped by `saved_at` then emits each day once. When `sort=published_desc` or `sort=title` returns saved days A, B, A, the table/list/card show IDs in order A1,B1,A2 but timeline emits A1,A2,B1. Membership remains equal, **global server order is not preserved**. `p11-collections.test.mjs` includes exact reproducer; fix should either display contiguous date runs without regrouping or explicitly document timeline view's sort override. **INTEGRATION_REQUIRED** for owner of `LibraryViews.tsx` (P01/G00); P11 does not edit it.
2. **LABEL-02 (source-confirmed):** table caption unconditionally says `Thứ tự nhận lần đầu, mới nhất trước` even if saved query requests `saved_asc`, `published_desc` or `title`. Repro: save `sort=title`, view `table`. Fix caption derive from active sort or neutral caption. **INTEGRATION_REQUIRED** for UI owner (P01/G00).
3. **SCHEMA-03 (source-inspection risk, execution pending):** `results` revalidates persisted JSON via `CollectionQuery.model_validate(value.query)` without catching `ValidationError` unlike `preview` handling of ValueError. A legacy schema/version-invalid JSON entry in database may cause HTTP 500 instead of a 422 or migration-safe error; test creates a synthetic invalid definition, must run before severity assigned. **INTEGRATION_REQUIRED** if reproduced. Do not silently discard stored definitions.
4. **PERF-04 (risk, needs PG measurement):** every HTTP page runs `COUNT(*)`, an OFFSET slice and summary prefetches, and `all` with up to 100 group IDs contributes up to 100 `EXISTS` predicates. Existing GIN/search and owner/saved indexes were reviewed, but **no P11 EXPLAIN ANALYZE/query-count/P95 evidence yet**. Keep actual query bound sample count and plans on disposable PG; do not assign SLA.

No demonstrated SQL injection: text is passed as parameters, sort is a Literal allowlist, group IDs are StrictInt and owner scope is explicit in match and relation subqueries. This is a source-review conclusion, not a penetration test.
