## Acceptance and metrics contract

For each positive-gold query: `relevant_returned = |top5 ∩ gold|`; micro recall = `sum(relevant_returned) / sum(|gold|)`; micro precision = `sum(relevant_returned) / sum(|top5|)`. Empty-gold queries are negative safety probes and excluded from positive precision/recall; false positives are reported separately. Zero denominator => `null`. Actual P95 is nearest-rank of measured in-process service durations in milliseconds, over exactly 86 PG-backed calls, **only after running** the opt-in harness.

## Risks / suspected gaps (not runtime-confirmed defects)

- Current SQL search uses Item / active DerivedContent / recent `raw_kind=link` CaptureEvent; Source metadata and RelatedItem are not searched. Semantic queries are intentionally challenging and may fail lexical FTS.
- `Source.metadata` may contain an unverified citation-like payload. A location field does not prove the quoted content; verify actual `derived_content_id` or `capture_event_id`.
- Capture history scan is capped at 1,000; full-history recall and large-data performance are unproven.
- Topic membership is M:N and owner-filtered, but needs runtime verification across two owners; a static SQL read is not a permission test.
- Gold itself is model-authored, not human adjudicated.
