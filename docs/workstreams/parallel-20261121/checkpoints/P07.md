## Protocol decision and fixture

- A request `Range: bytes=-6291456` against a 104857600-byte file now returns a clear **416** with `Content-Range: bytes */104857600`; it never fabricates a `206` for the wrong 4 MiB prefix of that 6 MiB suffix. A client can request the last 4 MiB, or use bounded closed ranges to fetch larger content in parts.
- Closed ranges exceeding 4 MiB similarly reject 416; `bytes=START-` continues returning a correctly labelled 206 for the capped slice. All individual provider reads remain <= 4 MiB.
- Synthetic `P` bytes serve only for deterministic header/seek assertions, **not** a claim of decoded PDF pages or playable MP4 in Chrome.
- Existing `DriveStorage.read_range` does remote revision/hash/size and owner checks before and after the requested slice; P07 does not bypass or change that path.
- Cache remains `private, no-store`, with same-origin CORP, no CORS opt-in. Cross-origin fetches are not enabled; a hosted viewer must share origin or G00 design a separate authenticated CORS contract.

## Risks, rollback, and G00 handoff

- **Known interoperability caveat:** Some PDF/media clients request >4 MiB suffix/closed ranges. They will receive a protocol-correct 416 rather than truncated data, but such clients may need an explicit chunking adapter or a protected streaming service. Do not expand the 4 MiB provider bound without revisiting transport memory safety.
- **INTEGRATION_REQUIRED:** G00 must run the Django test module and existing `storage.test_viewer` on disposable PostgreSQL, then browser-test a real synthetic PDF and MP4 with authentication and at least 20 actual seeks.
