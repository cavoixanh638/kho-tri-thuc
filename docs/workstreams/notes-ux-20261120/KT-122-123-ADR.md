# KT-122/123 placement and directed note structure

Baseline PR57 e00b3ca. No production migration/deploy is authorized.

| Choice | Migration, query and restore tradeoff |
| --- | --- |
| Item.home_topic nullable FK (chosen) | One stable location, no arbitrary sort-derived home. Existing ItemTopic retains all memberships. Owner/home/parent/order index supports bounded children reads. Existing Item backup/vault projection can preserve nullable UUID/FK fields. Old data stays unplaced until explicit choice; no guessed backfill. |
| is_primary on ItemTopic + conditional unique | Enforces one flagged membership but moving primary needs two relation updates and primary semantics can be erased by old classification/group replacement paths. Requires extra conditional uniqueness and restore sequencing. |
| Separate placement/preferences table | Flexible multiple layouts but adds another identity/version/backup collection and joins without a current multi-layout requirement. |

Directed structure choices: a nullable Item.parent_item FK is chosen over a
directed edge table or generic typed relation table. One direct parent is
enforced by the single FK, self-parent is prohibited in PostgreSQL, and owner
write locks plus ancestor checks serialize longer cycle checks. RelatedItem
and Markdown backlinks keep their existing meaning. outline_order,
structure_version and structure_origin=user belong to explicit structure,
not user_edit_version/raw note. No automatic parent inference.

Canonical appearance: a live structural parent takes precedence over home
folder. Direct folder memberships show shortcuts when a note has a live parent
or another home. Deleting/archiving a home folder never deletes the Item;
archived homes are displayed in the unfiled navigator until explicitly moved.
Soft-deleted/cross-owner parents are not followed, and children stay accessible.
Both relationships use SET_NULL for hard deletion. API mutations require an
active same-owner parent/home, expected structure version and owner row lock.

Manual home membership is pinned. Moving home preserves all secondary
memberships; removing a membership only clears home when removing that exact
home, and never destroys note/history/media. Reorganizing creates no jobs.
Creating a note delegates to CaptureService's durable transaction and an
internal placement callback, so receipt/Event/Item/home commit together.

Rollback: backup with the extended Item projection before reversing migrations.
0006→0005 drops structure columns, 0005→0004 drops home, retaining all Item,
ItemTopic, Asset, Source and CaptureEvent rows. Reverse schema cannot preserve
dropped relationship columns by itself; restore those from the pre-rollback
backup. Do not reverse-migrate production without explicit approval.
